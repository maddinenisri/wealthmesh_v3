## What the pattern says

Four slices in a row (02 to 05) the validator found a race or an unenforced rule after the build, and each fix was
written for the last bug: a state swap, a keyed save, a row, then a member. The next bug had a new shape, so the rule
did not fire. The Build step is now one table cell of about 330 words that the builder reads once and recalls from
memory.

## Proposals (owner decides; nothing applied)

1. **Checklist instead of prose.** Move the Build-step rules to `docs/process/build-checklist.md` as short yes/no items,
   and leave one line in the skill pointing to it.
2. **Inventory at checkpoint 1.** The task list names every shared row or state a group changes (account row, member
   status, entry) and every reader and writer of it, found by grep. Race tests are written from that list.
3. **Validator fills the checklist.** The validator brief includes the checklist; the report marks each item pass or
   fail with evidence. A blank item counts as a failure.
4. **A race-test helper.** One shared test helper that holds an uncommitted write on a second connection, so a lock test
   costs a few lines. In slice 05 the first race test passed without the lock; a helper removes that trap.
5. **Remove, not just add.** After slice 06, strike rows judged "not helping" from the skill and say so in
   `improvements.md`.
